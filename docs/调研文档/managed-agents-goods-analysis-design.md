> **版本**：V1.5

> **方案边界**：本方案仅覆盖火山引擎 Managed Agents 平台侧的对接设计、Agent 配置、Skill 集成、资源管理、会话与事件处理，不包含 leyosys 业务系统本身、业务语义口径定义、前端页面开发与业务侧后端服务。

## 一、项目概述

### 1.1 背景与目标

基于火山引擎 Managed Agents 构建商品分析取数 Agent，复用已开发完成的 leyosys 沙箱自定义取数能力，结合语义层（指标/维度/接口契约）将用户自然语言拆解为一次或多次取数接口调用，并把结果以可控方式交还给用户。本 Agent **不做**规则匹配、根因诊断、处置建议；诊断类能力若后续需要，另开分析链，不塞进本链路。

核心建设目标：

1.  复用 leyosys 自定义 Skill，按用户维度鉴权调用业务接口，实现多源数据按需拉取
2.  以语义层把用户输入拆成明确的接口 + 参数清单（查询计划），再编排取数
3.  分层交付取数结果：对话给查询计划、摘要与预览；大结果明细导出文件经平台文件服务下载（默认保留 7 天），不做长期归档
4.  支撑约 1000 名内部业务用户稳定使用，单次单用户原始数据量≤10MB

### 1.2 建设范围

- ✅ 一期（本版落地）：Agent 编排设计、自定义 Skill 集成、语义层静态配置（Skill 内）、会话管理、每用户独立 Memory Store、创建会话时直接注入用户凭据环境变量（不经过 Vault）、取数结果分层交付与平台文件导出、事件对接、成本与运维设计
- ⏭️ 二期（进阶）：Vault 凭据库迁移（需同步改造 leyosys/Skill，详见 3.4）；语义层抽离为业务侧配置源，支持热更新（口径由业务补齐后启动）
- ❌ 不包含：leyosys 业务系统开发、业务原始口径/指标定义本身、前端页面开发、业务侧后端服务、诊断/根因/处置建议

### 1.3 用户与使用模式

- 目标用户：约 1000 名内部业务运营/分析人员
- 触发方式：用户主动发送取数/查询指令触发任务
- 交互形态：单轮完整取数 + 多轮追问（改条件重查，或基于上一份结果切片/再导出）
- 鉴权粒度：leyosys 业务接口为**用户级独立鉴权**，每个用户凭据隔离；一期通过会话环境变量注入用户凭据，二期迁移 Vault
- 数据规模：单次任务累计原始数据量≤10MB；业务接口支持分页，取数过程分页拉取、边拉边写产物文件（内存仅驻留当前页，见 3.1.4）；默认不把整表写入模型上下文（仅 ≤50 条的小结果可整表进对话）

### 1.4 核心交付产物

1.  **对话交付**：查询计划（接口清单 + 参数）、结果摘要（行数/字段/时间范围）、前 N 行预览；仅当结果低于保守阈值时，整表可直接出现在对话中
2.  **取数结果文件**：默认 xlsx（多接口多 sheet），由平台文件服务托管分发，默认保留 **7 天**（业务确认无 30 天留存要求）；对话提供下载入口。一期不对程序侧另附 json（manifest sidecar 除外，见 3.3.2）

### 1.5 平台环境与版本说明

1. 本方案技术设计同时兼容**火山方舟 Managed Agents（标准版）**与**ArkClaw 企业版**，二者核心 API、Skill 开发规范、工具调用机制完全同源，开发逻辑可无缝复用。
2. ArkClaw 企业版「平台托管」模式属于标准企业版序列，完整享有企业版全部功能（原生 AGENTS.md 规则文件、企业级 Skill 管理、权限分级等），并非独立降级版本。
3. 本方案默认按最低兼容路径设计，确保快速上线；ArkClaw 企业版环境下可额外启用原生规则文件、企业级资源管控等增强能力，作为可选优化项。

## 二、整体架构与核心链路

### 2.1 总体架构分层

| 层级                  | 说明                                                         | 本方案范围             |
| --------------------- | ------------------------------------------------------------ | ---------------------- |
| 用户交互层            | 前端对话入口、文件下载与历史查询                             | 不涉及                 |
| 接入转发层            | Node.js 自研后端，负责用户鉴权、请求转发、事件透传、资源管理 | 仅涉及 MA 对接相关逻辑 |
| **MA 平台层（核心）** | 火山 Managed Agents 托管环境                                 | ✅ 本方案全覆盖        |
| 业务依赖层            | leyosys 业务系统接口；二期含语义层配置源                     | 不涉及，仅定义对接契约 |

MA 平台层内部拆解：

- **Agent 调度层**：大模型推理、指令解析、进入分析 Skill、转述查询计划与交付说明
- **Skill 执行层**：分析 Skill（语义规划 + 取数编排 + 结果打包）、leyosys 取数 Skill、内置文件写入能力
- **基础资源层**：沙箱运行环境、Memory Store（每用户独立库：用户配置 + 查询锚点 + 文件索引）、平台文件服务（结果产物托管，默认 7 天）；Vault（用户级凭据库）为二期进阶项

### 2.2 核心 Skill 分工与职责边界

| Skill 名称 | 形态 | 职责 | 输入 | 输出 |
| ---------- | ---- | ---- | ---- | ---- |
| leyosys 取数 Skill | 沙箱内自定义 Skill（已开发完成） | 按用户鉴权调用指定业务接口拉取数据 | 接口标识 + 查询参数 | 该接口的结构化结果（计入单用户单次≤10MB） |
| 分析 Skill（语义规划器） | 沙箱内自定义 Skill（分析主入口） | 加载语义层，将用户意图拆成接口调用清单，按 3.1.3 编排或收编取数能力执行，按 3.1.4 打包交付 | 用户自然语言意图 | 查询计划；交付说明（摘要/预览/是否整表进对话）；结果文件 `file_id` |
| Agent 主模型 | 平台内置大模型 | 指令理解、进入分析 Skill、向用户转述计划与交付说明、多轮追问 | 用户自然语言指令 | 最终文字回复（不含完整明细，除非低于阈值） |

> **待评审点：**
>
> 1. **Skill 形态说明（一期）**：leyosys 取数 Skill、分析 Skill 均按**沙箱内自定义 Skill**实现，Skill 在沙箱内直接发起 HTTP 请求（取数调 leyosys 接口），不采用 custom_tool 回调 Node 的链路；这与现有 prompt.md 架构一致，也是 Vault 二期改造（Skill 改为 Python 直连）的基础。若后续改为回调 Node 执行，需切换为 `agent.custom_tool_use` + `requires_action` 事件流。
> 2. **语义层口径待业务给出**：一期先把已确认部分写进分析 Skill 静态配置；口径未齐前，不可覆盖的意图必须明确拒答并列出缺哪些口径，禁止猜测映射。
> 3. **典型查询体积待业务补数**：分层阈值先按保守默认值落地（见 3.1.4），上线后用真实任务量校准。

### 2.3 完整执行主流程

1.  用户发送自然语言查询指令
2.  Node 后端校验用户身份，查询对应用户的会话与资源绑定关系
3.  Agent 进入分析 Skill；分析 Skill 加载语义层静态配置，将输入拆成一条或多条取数接口调用（含参数），形成查询计划
4.  分析 Skill 按 3.1.3 完成取数（方案 1：模型逐次调度独立取数 Skill；方案 2：进程内收编取数模块一次完成），可多次调用接口，使用当前用户独立凭据拉数（**分页拉取、边拉边写、累计 ≤10MB 达限即停**，见 3.1.4）
5.  分析 Skill 按 3.1.4 分层打包：大结果导出至沙箱产物目录（平台文件服务登记托管）；向模型只回传查询计划、摘要、预览、`file_id`（及是否允许整表进对话的小结果）
6.  Agent 向用户转述查询计划与交付说明，并给出文件下载入口（前端在 `session.status_idle` 后拉产物列表）
7.  Node 后端消费分析 Skill 输出的结构化 manifest（**通道待评审，见 3.3.2**），异步更新对应用户的 Memory Store：最近查询锚点、历史文件索引、用户偏好
8.  所有中间事件与最终文字结果通过 SSE 事件流推送至前端
9.  任务结束，会话进入 idle，沙箱停止计费；内存中的原始明细释放，结果文件由平台文件服务托管（默认 7 天），超期锚点同步清理

> 已确认项（原待评审点，已闭环）：
>
> 1. **持久化范围已定**：完整明细不进 Memory Store、不进模型上下文；结果文件只经平台文件服务托管、默认 7 天，不做长期归档（业务确认无 30 天留存要求）。原始接口响应仅在当轮沙箱内存中存在。

## 三、核心模块详细设计

### 3.1 自定义 Skill 集成设计

#### 3.1.1 leyosys 取数 Skill

- **部署形态**：沙箱内本地运行的自定义 Skill，随沙箱启动加载
- **鉴权方式（一期）**：通过创建 Session 时的 `environment_with_overrides` 注入该用户的 leyosys 鉴权凭据（会话级环境变量），Skill 内直接读取环境变量调用业务接口。凭据仅在会话创建时注入、运行期不可变，凭据轮换时由后端重建会话加载新凭据
- **二期演进**：迁移至 Vault `environment_variable` 凭据库，需同步改造 leyosys Skill 为 Python 直连（规避 Node 子进程占位符脱敏问题），详见 3.4
- **调用方式**：按查询计划多次执行，每次对应一个接口 + 一组参数，不做语义拆解；**具体由 Agent 调度还是收编进分析 Skill 进程内调用，见 3.1.3 两方案待评审**
- **返回约束（方案 1 下为硬性要求）**：若取数 Skill 作为独立工具被模型调度，其工具返回值必经模型上下文，只能返回行数/字段/摘要/文件 `file_id`，**严禁把完整结果集作为返回值**；明细在执行环节直接导出为产物文件
- **数据处理策略**：
  - 业务接口已确认支持分页：按固定页大小分页拉取，**边拉边增量写产物文件**（先写临时文件名，全部完成后原子更名，避免半成品被平台登记），内存仅驻留当前页 + 预览行 + 累计摘要；单次任务累计不超过 10MB，达限即停（见 3.1.4）
  - 取数结果**不**把整表写入模型上下文：方案 2（收编）下明细只在分析 Skill 进程内流转；方案 1（Agent 编排）下取数 Skill 返回值必经模型，故只能回摘要/`file_id`（见上文「返回约束」）
  - 大结果导出到沙箱产物目录，由平台文件服务托管（默认 7 天，见 3.5）；不挂载私有 TOS、不在沙箱本地另做持久化副本
  - 当轮结束后内存明细释放；7 天内可经文件服务下载/同沙箱回读，超期或沙箱回收后按查询计划重取（见 3.1.4 追问约定）
- **用户隔离**：不同用户会话注入各自的环境变量凭据，沙箱与会话完全隔离，无交叉访问风险
- **超时配置（分两层，参照现有项目实现）**：
  - **Node 等待 Agent 事件：不设总超时**。HTTP 服务关闭 Node 默认超时（`requestTimeout/headersTimeout/timeout = 0`）；事件轮询的无进展超时与单轮硬截止默认均为无限，收口依赖 `user.interrupt` 与客户端断连（AbortSignal）。长取数不会被等待侧误杀
  - **Skill → leyosys 单页请求：必须设单页 HTTP 超时**（**初值灰度期定**），超时按 5.2 退避重试；重试预算只覆盖单页，不能让一个慢接口无限占用沙箱。可选配「连续 N 秒无任何新事件」的无进展告警（仅告警/提示用户是否中断，不做强制失败）
- **错误约定**：标准化错误码与错误信息，Agent 可根据错误类型给出对应话术

#### 3.1.2 语义层设计

##### 定位

语义层是分析 Skill 把自然语言映射为「接口 + 参数」的唯一依据，包含：可用接口、指标/维度含义、参数约束、实体别名与权限边界。它**不是**诊断规则库，也不产出根因或处置建议。

##### 一期：写入分析 Skill 静态配置

业务原始口径尚未齐备，一期采用 Skill 包内静态配置：

1.  **存储位置**：分析 Skill 包内的配置文件（与执行器代码分离，便于口径补齐后只改配置、少改代码）
2.  **加载方式**：分析 Skill 每次执行时从包内读取，内存处理，不写 Memory Store
3.  **生效时机**：更新配置需发布新的 Skill 包版本；**不中断已有会话对象**，但已启动沙箱需在新任务加载到新包后才生效（以平台 Skill 发布行为为准）
4.  **未覆盖意图**：语义层无法映射时，明确告知无法取数及缺失口径，禁止猜测接口或参数
5.  **版本**：配置带版本号，随 Skill 包发布记录，便于对照「这次查询用的是哪一版口径」

##### 二期：抽离为业务侧配置源（口径齐备后）

复用原「规则与执行器解耦」思路，仅替换承载内容：

1.  语义层数据改由业务侧配置源统一维护，不进 Memory Store
2.  分析 Skill 每次执行拉取最新全量语义配置（内存处理）
3.  无需重建沙箱、无需中断在线会话，全量用户下次执行即生效
4.  配置带版本号，业务侧保留最近 3 个历史版本；回滚在配置源完成
5.  加载失败按 5.1 重试；仍失败则拒答，不用过期/残缺语义层硬猜

##### 与旧「业务分析规则」的关系

V1.2 中的规则执行、异常分级、根因诊断**不再属于本 Agent**。原 3.1.2 热更新方案的技术形态（执行器与数据解耦、配置源实时拉取）保留给二期语义层，不保留诊断语义。

#### 3.1.3 Skill 间协作机制（**两种编排方案，待评审二选一**）

> **平台约束（已确认）**：沙箱内一个 Skill 不能以编程方式直接调用另一个 Skill；跨 Skill 调用必须经 Agent（模型）按工具调用编排。因此 V1.3 中「分析 Skill 在沙箱内直接依赖并调用取数 Skill、返回值不经模型」的写法不成立，需在以下两个方案中选定一个。语义拆解始终只在分析 Skill 内完成，取数 Skill 不理解自然语言——这一点两方案不变。

**方案 1：Agent 编排两个独立 Skill**

- 调度顺序：
  1. Agent 调分析 Skill，产出查询计划（接口 + 参数清单，带校验清单）
  2. 模型按计划逐次（或有限并行，受单会话与超时约束）调用 leyosys 取数 Skill
  3. 模型再调分析 Skill 做汇总核对与打包
- 代价与约束：
  1. 取数 Skill 的返回值是工具调用结果，**必经模型上下文**——截断职责必须下沉到取数 Skill：它只能返回「行数/字段/摘要/文件 `file_id`」，明细不得作为返回值，需在执行环节直接导出为产物文件
  2. 「计划 N 个接口就调 N 次、参数不被篡改」依赖模型严格执行，存在漏调/多调/改参风险，需分析 Skill 末轮按校验清单核对，缺失则要求补齐或明确告知
  3. 多轮工具往返推高 token 与耗时
  4. **分页循环不能摊到模型往返上**：业务接口已确认支持分页，翻页/累计/边写必须全部收敛在取数 Skill 的**单次调用内部**完成（一次工具调用内部自行翻完所有页，只回最终摘要/锚点）。若每页都由模型调一次工具，一个数百条结果会产生十几次往返，token、延迟与漏页风险均不可接受。这使方案 1 的可行形态其实接近方案 2，只剩「取数代码是否独立成 Skill 包」的差别
- 优点：两 Skill 保持单一职责、独立版本发布；取数 Skill 可被其他 Agent 复用

**方案 2：取数能力收编进分析 Skill（推荐候选）**

- 形态：分析 Skill 一个入口、一次工具调用，在其进程内部完成「语义拆解 → 查询计划 → 逐接口取数 → 打包导出产物文件」。现有已开发完成的 leyosys 取数逻辑以**同沙箱本地模块/函数**方式被分析 Skill 引用复用（**Skill 包之间能否做本地依赖、以什么形式打包，待 POC**），不再作为独立 Skill 被模型调度
- 优点：明细全程不出 Skill 进程，天然满足「完整明细不进模型上下文」；计划与执行原子完成，不依赖模型逐次遵守计划；工具往返与 token 最省
- 分页契合度：翻页/累计/边写是 Skill 进程内的普通循环，无任何模型往返，与 3.1.4 流式守卫天然契合，实现最直接（方案 1 也必须把分页收敛进取数 Skill 单次调用内部，见方案 1 约束 4，否则不可行）
- 代价：分析 Skill 包变大、职责变重；取数能力不能再以独立 Skill 形态被其他 Agent 复用（如有复用需求，抽成共享库由各 Skill 引用）
- 异常处理（两方案通用）：任一接口失败则该接口记失败，其余已成功接口仍可按 3.1.4 交付（部分成功）；分析 Skill 自身失败则本轮终止，已写出的文件保留并在回复中说明

> **待评审：二选一。** 选方案 1 需补：取数 Skill 的返回 schema（只回摘要/`file_id`）、明细导出与打包在多次调用之间如何衔接、计划执行核对机制；选方案 2 需 POC：Skill 包内引用现有取数 Skill 代码的打包方式、沙箱网络出口与凭据读取在收编后是否保持不变。

#### 3.1.4 结果分层交付（方案 C 骨架）

**硬规则：完整取数明细不进入模型上下文。** 这与业务暂时给不出典型体积无关，现在就可以定。

| 结果规模 | 对话里给什么 | 是否导出文件 |
| -------- | ------------ | ------------ |
| 空结果 | 空值说明 + 本次查询计划 | 否 |
| 小结果（≤50 条） | 查询计划 + 完整表格 | 是（方便下载与短期追问回读） |
| 大结果（>50 条） | 查询计划 + 摘要 + 前 N 行预览 + 下载说明 | 是 |
| 超限（单次合计 >10MB） | 提示缩小范围、分批再查 | 否（半成品不落） |

**默认阈值（可配，灰度期校准）**：

- 整表进对话：以**条数**为主阈值，单接口结果 **≤50 条**整表进对话——超过 50 条业务上基本不会在对话框内继续做分析，统一走文件；多接口时任一接口超过 50 条，则全部按「大结果」处理
- **字节兜底**：另保留一个宽松字节上限防止超宽行（**初值待定，灰度期校准**）；即使不足 50 条，触达字节上限也按大结果处理
- **10MB 硬上限的执行方式（业务接口已确认支持分页）**：50 条是「进不进对话」的阈值，10MB 仍是「单次任务能否承载」的硬上限。取数按固定页大小**分页拉取、边拉边累计**：
  1. 每页返回后累计总条数与总字节数，并**增量写入**产物文件（临时文件名，完成后原子更名），内存中只保留当前页 + 前 10 行预览 + 累计摘要（不做全量驻留）；
  2. 累计超过 50 条即标记为「大结果」，后续页只写文件、不进对话，不拉完也能确定交付形态；
  3. 累计字节数达 10MB **立即停止翻页**，删除本次半成品文件（确保不被平台文件服务登记），提示缩小范围分批再查（不以部分结果冒充全量交付）；
  4. 页大小取「单页字节明显小于 10MB」的保守值，确保最坏在一页内发现超限，**具体值灰度期校准**。
- 预览行数 **N = 10**
- 文件格式：xlsx；多接口一张工作簿、一个接口一张 sheet
- 灰度期拿到真实结果**条数分布**后再评估是否上调 50 条；若上线后「整表进对话」占比长期接近 0，阈值作废，退化成一律文件（方案 B）

**追问约定（避免「模型丢了整表」被误当成数据丢失）**：

1.  每轮必须留下锚点：`request_id`、接口清单、参数、行数、字段、结果文件 `file_id`。对话与 Memory Store 各存一份，防止长对话被平台截断后找不到上一份结果
2.  **默认重取**：用户改时间、维度、筛选条件时，按新参数重新打接口，旧文件不当唯一真相
3.  **仅当用户明确基于「刚才那份结果」切片/排序/再导出时**，分析 Skill 优先回读已有产物：沙箱存活期内直接读；沙箱已回收时能否经文件服务重新获取（见 3.5.1 POC），不能则按锚点查询计划重取；文件超 7 天被平台删除时一律重取，并向用户说明
4.  模型不得根据预览行对全量下结论
5.  锚点与文件索引随平台文件 7 天有效期同步清理（见 3.3.3）；超期追问即重取，不依赖本地残留

### 3.2 会话管理设计

#### 3.2.1 会话复用策略

- **策略**：**一人一会话（one user one session）**，1000 用户对应约 1000 个常驻 session
- **理由**：
  1.  用户主动触发、多轮追问场景多，复用会话保留查询计划与摘要，提升改条件重查的连贯性
  2.  资源（Memory Store、会话环境变量）一次挂载/注入，全程生效，避免重复创建开销
  3.  沙箱 30 天无活跃自动回收，闲置用户不产生运行成本
  4.  一期语义层随 Skill 包发布；二期热更新不依赖会话重建
- **冷启动**：沙箱被回收后，该用户下一轮需重新拉起沙箱、加载 Skill 包与语义配置、挂载 Memory，产生额外等待与 running 计费；7.1 的单次时长假设需把冷启动算进去。灰度期观测冷启动 P95 耗时与命中率（见 8.2），若偏高可对活跃用户保活
- **边界**：同一用户多次查询复用同一会话，不同用户会话完全隔离，数据不互通
- **并发限制**：同一 Session 不支持并发发送两条消息（平台约束）。同一用户并发的取数请求需由后端排队或拒绝（返回"上一任务进行中"），避免第二个请求覆盖或报错；如需并行查询，需为该用户创建临时独立会话，代价是上下文不复用

#### 3.2.2 交互模式

- 支持单轮一次性完整取数
- 支持多轮追问：调整时间/维度/筛选后重取；或基于上一份结果文件切片、再导出
- 对话上下文保留查询计划与摘要；完整明细以文件 + Memory Store 锚点为准，不依赖模型「记住整张表」
- 平台会话事件流仍是对话历史载体，无需业务侧另存聊天记录

#### 3.2.3 中断机制

- 长耗时取数过程中，支持通过 `user.interrupt` 事件中止当前任务
- 中断仅终止当前执行轮次，不销毁沙箱、不删除会话；已写出的部分文件保留并在回复中说明，后续可继续发起新查询

### 3.3 Memory Store 场景化设计

#### 3.3.1 存储内容清单

| 存储项 | 说明 | 更新方 |
| ------ | ---- | ------ |
| 用户查询偏好 | 常用维度、默认时间范围、输出格式偏好、默认品类权限 | Node 后端 |
| 最近查询锚点 | 最近 N 次（建议 20）的 `request_id`、查询计划、行数、结果文件 `file_id`（7 天有效）、语义层配置版本 | Node 后端 |
| 历史结果文件索引 | 任务 ID、时间、摘要、平台文件 `file_id`、文件名、文件大小（与锚点可合并为单条 JSON） | Node 后端 |
| 用户权限标识 | 可访问的商品品类、数据范围权限标记 | Node 后端 |

> **不存储**：原始业务明细、完整结果集、分析 Skill 代码、语义层全量配置（一期在 Skill 包内，二期在业务侧配置源）

#### 3.3.2 读写策略

- **读权限**：沙箱以 `read_only` 模式挂载对应用户的 Memory Store，Skill 运行时读取用户配置、锚点与索引
- **写权限**：统一由 Node 后端通过 Memory Store API 执行写入/更新，Skill 不具备写权限，避免数据篡改
- **更新时机**：用户配置变更、完成新的取数任务时，由后端异步更新对应用户的库

> **待评审（锚点数据通道）**：写入方是 Node，但查询计划、行数、`file_id` 都产生于沙箱内分析 Skill，Node 只能从事件流旁观；`agent.message` 是给用户看的自然语言，不能作为解析来源。需定义**结构化 manifest 通道**：分析 Skill 每轮结束输出一份固定 schema 的 JSON（`request_id`、接口清单与参数、行数、字段、结果文件 `file_id`/文件名、语义层配置版本），Node 直接消费后落 Memory Store。候选载体：
>
> 1. **（推荐候选）** Skill 将 manifest 作为 sidecar 文件与结果 xlsx 同批写入沙箱产物目录（约定 `.manifest.json` 后缀），随产物一起登记到平台文件服务；Node 在 `session.status_idle` 后经 `GET /files` 拉取读取（与产物轮询合并），并在对用户的文件列表中按后缀过滤隐藏。manifest 由 Skill 代码直接落盘、**不进工具返回值**，模型侧 token 成本约为 0，工具返回只留一句模型本来就要转述的摘要；可行性与 3.5.1 的文件服务 POC 合并验证；
> 2. Node 从结构化的工具结果事件取（**事件是否暴露工具结果、字段是否完整，待 POC**）；代价：工具结果即模型输入，manifest 会全额进入上下文；
> 3. 不建议给 Skill 开 Memory Store 写权限——与「Skill 只读、Node 统一写」的防篡改设计冲突。
>
> **Token 影响评估（结论：不构成大量额外消耗）**：manifest 是与结果行数无关的有界元数据，体积只随接口数/列数增长。粗估单接口 100～250 tokens、单次查询（1～5 个接口）约 0.2～1.3k tokens，占 10k/次预算的 2%～13%；且其中查询计划/摘要本就要在对话给出，边际开销主要是 JSON 语法与 `file_id`/版本号。采用候选 1 时该开销不发生。schema 约束：超长参数（如大批量商品编码）必须截断为「前 N 个 + 总数」，不得整列入 manifest。
>
> 另需明确：Node 异步写入完成前，锚点不可见，追问若依赖锚点需以后端写入完成作为就绪信号。

#### 3.3.3 容量与生命周期

- **方案选择**：**每用户一个独立 Memory Store**（1000 用户对应约 1000 个库），会话创建时以 `resources[]` 挂载对应用户库
- **容量规划**：
  - 单用户库条目数：3~5 条（偏好、锚点+文件索引、权限标识等），单条 ≤100KB，远低于单库 2000 条上限
  - 锚点与文件索引合并为每用户 1 条 JSON（数组内追加，超出 N 条淘汰最旧），避免「每次查询 1 条」导致条数失控
  - 语义层全量配置不占 Memory Store
- **生命周期**：
  - 用户级数据：随用户账号生命周期，离职/失效用户同步清理
  - 文件索引 / 锚点：与平台结果文件生命周期同步（默认 7 天），文件到期删除时同步清理对应条目；查询计划本身可保留更久（重取不依赖旧文件）

### 3.4 凭据管理设计（一期：会话环境变量；二期：Vault 进阶）

#### 3.4.1 一期方案（本版落地）

- **注入方式**：创建 Session 时通过 `environment_with_overrides` 注入该用户的 leyosys 鉴权凭据（会话级环境变量），Skill 内直接读取环境变量调用业务接口
- **有效期与重建时机**：环境变量仅在会话创建时注入、运行期不可变。leyosys Token 业务侧确认为**长期有效（不过期）**，一期常态下不因到期轮换而重建会话；仅在用户离职、权限变更或凭据主动撤销/疑似泄露时，由后端删除或重建会话使旧凭据失效
- **安全边界**：凭据明文存在于沙箱环境变量中，但沙箱按用户隔离；后端不向前端暴露凭据，日志/事件流不打印完整凭据
- **隔离性**：不同用户会话注入各自凭据，沙箱与会话完全隔离

#### 3.4.2 二期进阶：Vault 凭据库（需同步改造 leyosys/Skill）

> 说明：一期不采用 Vault，原因有二：① 迁移需同步改造 leyosys 取数 Skill；② 现有 Skill 形态存在 Node 子进程读取环境变量时占位符被脱敏为 `SECRET_PLACEHOLDER`、网关无法替换、鉴权失败的问题。

- **粒度**：**一用户一 Vault**，每个用户独立凭据库，库内仅存放 1 条 `environment_variable` 类型凭据
- **改造前提**：leyosys 取数 Skill 改为 Python 直接发起 HTTP（不拉起 Node 子进程读环境变量），规避占位符脱敏问题
- **待 POC 验证项**：凭据更新（PUT）是否对已运行会话实时生效，需以官方 Vault 文档与验收用例为准，正式上线前不得作为结论写死
- **隔离性**：不同用户 Vault 完全独立，会话之间凭据不互通

#### 3.4.3 资源绑定关系

通过业务映射表 `user_agent_bind` 统一维护：
`biz_user_id ↔ memory_store_id ↔ default_session_id`（二期接入 Vault 后追加 `vault_id`）

### 3.5 结果文件交付设计（平台默认文件服务）

#### 3.5.1 交付方案

不挂载私有 TOS 桶，大结果直接使用平台默认文件能力：

- **导出方式**：分析 Skill 将结果文件写入沙箱产物目录（先临时文件名、完成后原子更名），平台自动登记为会话产物
- **下载方式**：前端在 `session.status_idle` 后通过 `GET /files?scope_id={sessionId}` 拉产物列表并取下载链接（方舟原生事件中无 `file` 事件，见 4.2）
- **保留期**：平台默认 **7 天自动删除**。业务已确认结果文件无 30 天留存要求；如未来提出长期归档需求，再另行评估私有存储/业务侧归档，**不进一、二期承诺**
- **追问回读**：沙箱存活期内可直接回读产物；沙箱回收后能否经文件服务重新获取历史产物见下方 POC；文件超 7 天被删除时按锚点查询计划重取（见 3.1.4）

> **待 POC（平台文件服务链路，一期上线前必须闭环）**：
>
> 1. 沙箱 Skill 写入产物目录的文件能否稳定出现在 `GET /files?scope_id=` 列表、下载链接是否可用、`scope_id` 是否即 sessionId；
> 2. 文件保留期与删除行为是否确为 7 天；**沙箱 idle/回收后文件是否仍可下载**（决定文件回读的可用窗口）；
> 3. 3.3.2 的 `.manifest.json` sidecar 能否同通道被 Node 读取、且 Node 能按后缀对前端过滤隐藏；
> 4. 平台默认文件存储的**租户隔离能力与内部商品数据密级是否匹配**，需安全侧确认；
> 5. 平台对单文件大小/单会话产物数量是否有限额（接近 10MB 的文件需实测）。

#### 3.5.2 命名与索引

- 文件命名：`query_{时间}_{request_id}.xlsx`；多接口一张工作簿、一个接口一张 sheet
- manifest sidecar：`query_{时间}_{request_id}.manifest.json`（供 Node 消费，不对用户展示）
- 索引关联：文件生成后，`file_id`、文件名、大小、时间、查询计划摘要写入 Memory Store（见 3.3.1）；文件 7 天到期后索引同步清理（见 3.3.3）

#### 3.5.3 失败处理

- 导出过程中 Skill 失败/任务中断：临时文件名未更名前不被平台登记，不会产生残缺产物；已完成更名的文件保留，回复中说明
- 平台文件服务异常导致登记失败：本轮按失败处理并告警，不做「沙箱本地暂存后台重试」（沙箱 idle 即回收，无补偿执行主体，见 5.1）

### 3.6 语义内聚与功能解耦设计

#### 3.6.1 核心设计原则

严守两条设计红线：

1. **不修改 Agent 原始主提示词**：主提示词仅保留角色定位、行为边界与工具调用总原则，不写入具体指标口径、接口映射与参数约束，保持长期稳定。
2. **不篡改用户原始输入**：用户自然语言输入原样透传，不在后端强行拼接参数或补充内部信息，保证对话历史一致性。

所有语义映射、取数编排、结果打包全部下沉至自定义 Skill 层，兼顾保密性与独立迭代能力。

#### 3.6.2 能力分层承载

| 层级 | 承载形态 | 更新方式 | 迭代频率 |
| ---- | -------- | -------- | -------- |
| 框架层（行为边界、交付总规范） | 极简系统主提示词 | Agent 配置变更 | 极低 |
| 执行层（拆解流程、编排、打包） | 分析 Skill | Skill 包版本发布 | 中 |
| 语义数据层（接口、指标、维度、参数约束） | 一期：Skill 包内静态配置；二期：业务侧配置源 | 一期随包发布；二期 API 热更新 | 高（随口径补齐） |

语义口径全部内聚于 Skill 配置或业务配置源，控制台仅可见 Skill 名称与功能描述，满足高保密要求。

#### 3.6.3 功能解耦与工具拆分

按单一职责拆分，独立迭代：

- **商品信息标准化工具**（二期可拆）：商品名称/别名转标准编码、属性映射与权限校验
- **leyosys 取数 Skill**：按接口 + 参数拉数，按用户鉴权隔离
- **分析 Skill**：语义拆解、生成查询计划、编排取数、分层打包，本链路唯一业务入口
- **结果打包**：一期内聚在分析 Skill 内写 xlsx；二期若格式种类变多再拆独立工具

取数能力由分析 Skill 按 3.1.3 编排或收编；无论哪种方案，给模型的只是计划/摘要/预览，不是整表。

#### 3.6.4 工具调用管控机制

采用「模型自主调度 + 后端 `tool_choice` 边界约束 + Skill 入口校验」机制，确保取数类任务必须走工具，禁止模型空口编造数据。**一期 Node 不做请求去重、不做事件流自动补发**，重复/补发一律按新任务由 Agent 执行，避免重复取数、重复落文件。

1. **后端边界约束（`tool_choice`）**：所有工具提前注入 Agent 自定义工具列表。后端仅做粗粒度意图分类，通过 `tool_choice` 划定边界：取数/查询类请求设为 `required`（强制调用工具）；闲聊等非取数请求设为 `auto`。（**待 POC：`tool_choice=required` 对沙箱自定义 Skill 是否可强制，还是仅对 custom tool 生效**）
2. **Skill 入口合法性校验**：分析 Skill 校验意图是否被语义层覆盖、参数是否落在约束内；取数 Skill 校验接口与权限。不通过返回标准化错误，禁止跳过执行。

#### 3.6.5 分阶段落地

1. **一期（本版）**：语义层静态配置 + 分析 Skill 内聚拆解/编排/打包，跑通「输入 → 计划 → 取数 → 分层交付」。
2. **二期**：Vault 迁移；语义层抽到业务配置源；标准化工具按需拆出。
3. **三期**：用真实体积分布校准 3.1.4 阈值；若整表进对话长期无用，退化成一律文件。

## 四、接口与事件规范

### 4.1 平台侧核心 API 清单（Node 后端调用）

| 类别             | 接口                                 | 用途                                                      |
| ---------------- | ------------------------------------ | --------------------------------------------------------- |
| 资源管理         | 创建 Memory Store、写入/删除记忆条目 | 用户配置、查询锚点、文件索引（每用户一库）                |
| 会话管理         | 创建 Session                         | 挂载用户 Memory Store，注入用户凭据环境变量              |
| 会话管理         | 发送用户事件                         | 提交查询指令、中断任务                                    |
| 事件流           | 查询会话事件列表（项目现状：500ms 轮询；平台亦支持 SSE） | 监听消息、Skill 调用、状态等事件                |
| 文件管理         | 获取文件下载链接                     | 取数结果文件分发；`GET /files?scope_id={sessionId}` 拉产物 |
| 资源管理（二期） | 创建 Vault、写入/更新凭据            | 用户级凭据生命周期管理（Vault 迁移后启用）                |

### 4.2 SSE 核心事件类型与处理逻辑

| 事件类型                                   | 触发时机                              | 处理逻辑                                                                               |
| ------------------------------------------ | ------------------------------------- | -------------------------------------------------------------------------------------- |
| `agent.message`                            | Agent 生成文字回复                    | 增量推送至前端（计划/摘要/预览，不是整表明细，除非低于阈值）                           |
| `session.status_idle`（`requires_action`） | 等待 custom tool 回传结果             | **不算本轮结束**，回传 `user.custom_tool_result` 后继续；一期沙箱 Skill 场景一般不触发 |
| `session.status_idle`（真正空闲）          | 本轮取数任务结束                      | 标记任务完成、停止计时、轮询产物文件、异步更新锚点与索引                               |
| `agent.custom_tool_use`                    | custom tool 开始执行（二期/回调链路） | 记录日志、前端展示执行状态                                                             |

> 说明：① 事件类型以官方「会话事件类型」文档为准，custom tool 事件带 `agent.` 前缀；② 方舟原生事件中未见 `file` 事件，产物文件在 `session.status_idle` 后通过 `GET /files?scope_id={sessionId}` 轮询获取，再更新索引并向前端提供下载链接；③ 后端向前端透出的 `error` 为归一化错误事件，非方舟原生事件名；④ **事件获取方式以现有项目实现为准：500ms 短轮询 `GET /sessions/{sessionId}/events`**（按事件 id 去重，天然支持断连后继续；实现中另有「收到最终回复后 8s 未收到 idle 即正常收口」的兼容处理）。平台虽提供 SSE 长连接与 `Last-Event-ID`，一期不强制切换；如下文仍以「SSE/事件流」表述，均同时涵盖轮询实现。

## 五、可靠性与异常处理

### 5.1 核心异常场景与处理

| 异常场景 | 触发原因 | 处理策略 |
| -------- | -------- | -------- |
| 取数 Skill 鉴权失败 | Token 被撤销/疑似泄露吊销、用户权限变更（Token 本身长期有效） | 返回鉴权失败提示，引导联系管理员重新签发，由后端重建会话加载新凭据；记录审计日志 |
| 取数 Skill 执行失败 | 接口超时、参数错误、数据为空 | 返回明确错误话术；数据为空给出空值说明；多接口时已成功部分仍可交付 |
| 语义层无法映射 | 口径未覆盖、配置缺失 | 明确拒答并列出缺失口径，禁止猜测接口或参数 |
| 语义层加载失败（二期） | 业务侧配置源不可用、版本不兼容 | 按重试策略重试；仍失败则拒答，不用残缺配置硬猜 |
| 数据量超限 | 单次合计超过 10MB | 提示缩小查询范围，分批再查；不落完整文件，避免沙箱内存溢出 |
| 追问回读失败 | 平台文件已过 7 天被删、沙箱回收后不可重新获取 | 说明原因，按锚点中的原查询计划重取；禁止用预览冒充全量 |
| 单页取数超时 | leyosys 单页接口超时 | 按 5.2 单页退避重试；仍失败则该接口记失败，已成功接口按部分成功交付。等待 Agent 事件侧不设总超时，任务收口靠用户 `user.interrupt` 或客户端断连 |
| 事件通道断开（SSE 断连 / 轮询请求失败） | 网络波动、代理超时 | 轮询实现：下个周期自动续拉、按事件 id 去重，任务本身在平台侧继续；SSE 若启用则自动重连 + `Last-Event-ID`；等待侧无总超时，不因等待误杀长取数 |
| 模型调用失败 | 限流、服务异常 | 重试 1 次，仍失败则返回友好提示，记录告警 |
| 结果文件导出/登记失败 | Skill 导出异常、平台文件服务异常 | 本轮按失败处理并明确告知用户、记录告警；临时文件名未更名前不产生残缺产物；**不**做沙箱本地暂存后台重试（沙箱 idle 即回收，无补偿执行主体，见 3.5.3） |

### 5.2 重试与幂等

- **重试策略**：取数接口按**单页**指数退避重试 3 次（重试预算不跨页累积）；二期语义配置加载重试 2 次；模型调用失败重试 1 次；事件轮询请求失败按下个轮询周期继续，不影响进行中的任务（等待侧无总超时）
- **请求追踪（一期不做去重）**：每次取数任务携带唯一 `request_id`，用于日志关联与审计追溯（见 6.3）。一期 Node 不做请求去重，重复请求按新任务正常交由 Agent 执行，可能产生新的取数调用与结果文件；同 Session 的并发消息仍由后端排队/拒绝（平台硬约束，见 3.2.1，与去重无关）
- **断点续传**：轮询实现按已见事件 id 集合去重，断连恢复后续拉不重复推送；若改用 SSE，则用 `Last-Event-ID` 从断点继续

## 六、安全与合规

### 6.1 凭据安全

- 一期：用户凭据经会话环境变量按用户隔离注入，仅沙箱内可读，不向前端暴露，日志/事件流不打印完整凭据
- leyosys Token 长期有效、无到期轮换，须配套泄露吊销与离职/权限变更即时回收会话的流程、全程会话事件审计（见 6.3）；长期凭据是二期迁移 Vault 的主要动因之一（网关占位符替换，沙箱内不落明文）
- 二期（Vault）：一用户一 Vault，密钥只写不可读，出站网关替换，沙箱/事件流/日志不出现明文；迁移前需完成 3.4.2 的 POC 验证
- 最小权限原则：仅注入业务接口调用所必需的凭据

### 6.2 数据安全

- 业务原始明细仅在当轮沙箱内存中处理，大结果只导出为平台文件服务的会话产物（默认 7 天删除），不写入 Memory Store，不进入模型上下文（低于阈值的小表除外）
- Memory Store 仅存用户配置、查询锚点与文件索引，不存储原始业务明细与语义层全量配置
- 平台文件服务按租户/会话隔离，下载走平台鉴权链接；**隔离机制与内部商品数据密级的匹配性待安全确认（见 3.5.1 POC）**，文件 7 天自动删除
- 不同用户会话、沙箱、资源完全隔离，数据不互通

### 6.3 审计追溯

- 所有 Skill 调用、文件生成、任务执行均有完整会话事件日志
- 支持按 `session_id`、`biz_user_id`、`request_id` 追溯查询计划、接口参数与结果文件
- 语义层配置发布、凭据更新均留存操作日志，可审计

## 八、运维与可观测性

### 8.1 日志体系

- 会话事件日志：平台原生完整事件流，用于全链路排查
- Skill 执行日志：沙箱内标准输出，用于定位拆解、取数、打包报错
- 接入层日志：Node 后端请求、SSE 连接、重连、错误、产物轮询日志

### 8.2 核心监控指标

- 业务指标：在线会话数、日任务量、任务成功率、平均响应时长、查询计划接口数、部分成功占比
- 资源指标：沙箱运行时长、冷启动耗时 P95 与冷启动命中率、Token 消耗量、结果文件生成量、单文件大小/条数分布、平台文件存量与到期量、单页取数耗时与重试次数
- 异常指标：错误率、SSE 重连次数、Skill 失败率、鉴权失败率、语义层无法映射次数、追问回读失败次数
- 交付指标：整表进对话占比、预览+文件占比、超限拒绝占比（用于校准 3.1.4 阈值）
- 语义指标（二期）：配置更新频率、加载成功率、版本分布

### 8.3 排障路径

1.  按 `session_id` / `request_id` 拉取完整会话事件流，定位失败节点
2.  查看分析 Skill / 取数 Skill 执行日志，核对接口、参数、语义配置版本
3.  核对 Memory Store 锚点、平台文件 `file_id` 与下载链路，以及会话环境变量注入（二期含 Vault）
4.  核查模型调用与限流情况
5.  映射失败时核对本轮使用的语义层配置版本与未覆盖字段

## 九、方案落地实施建议

1.  **一期优先落地核心链路**：用户会话管理 + 每用户 Memory Store + 会话环境变量凭据 + 分析 Skill（语义静态配置 + 拆解编排）+ leyosys 取数 Skill + 分层交付与平台文件导出，验证「输入 → 计划 → 取数 → 计划/摘要/预览/文件下载」通畅；**3.5.1 文件服务 POC 先行**
2.  **一期并行依赖（不挡平台对接，挡业务覆盖面）**：业务补齐语义口径后扩静态配置；业务补齐典型体积后校准阈值
3.  **二期扩展能力**：Vault 凭据库迁移（同步改造 leyosys/Skill）、语义层配置源热更新、精细化权限、历史查询体验优化（结果文件 7 天后只能重取，如业务需要长期留存再单独立项）
4.  **灰度验证**：先小范围用户试点，重点看拆解正确率、结果体积/条数分布、Token、平台文件链路稳定性，再全量推广
5.  **预案准备**：语义未覆盖时明确拒答；平台异常时准备降级路径（例如只暴露已配置好的固定取数入口）
